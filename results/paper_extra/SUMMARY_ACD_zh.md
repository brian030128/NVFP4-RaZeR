### A-3. 機制

**Tile 內的偏好幾乎都是混合的。**
- 把 1x16 的選擇按 tile 分組，≥ 99.999% 的 tile 同時含有兩種格式。
- 少數格式在 tile 中的占比：IF4 和 Zou 是 36.5–38.1%，Zou + FourOverSix 是 42.1–46.4%。這接近各 block 獨立選擇時的預期值，表示偏好在 tile 尺度上並不聚集。

**加總誤差後，結果等於多數決。**
- IF4 和 Zou 有 62–63% 的 block 偏好均勻格式。粗化後，均勻格式的占比變成：8x64 為 91–94.5%，16x64 為 96–98.4%，256x64 為 99.1–99.7%。
- Zou + FourOverSix 在 1x16 是 53–54%。到 256x64 時，Llama 降到 41%，Mistral 降到 36%，Phi-4 反而升到 69%。
- FlipQuant 的 E0M3 占比：8x64 為 1.6–2.5%，16x64 為 2.2–3.3%，256x64 為 6.4–10.0%。

**權重誤差預測不了 loss。**
- Zou + FourOverSix 在 8x64 的權重平方誤差比 FourOverSix 少 3.7–4.4%，但 ΔNLL 落在 −0.0016 到 +0.0029：6 組中只有 1 組顯著較好，2 組顯著變差。
- FlipQuant 在 8x64 的權重誤差和 FourOverSix 幾乎一樣（−0.0% 到 +0.1%），卻全部顯著較好：
  - Llama：−0.0141 / −0.0141
  - Mistral：−0.0059 / −0.0058
  - Phi-4：−0.0077 / −0.0049

### A-4. 事後分析（未登錄）

- FlipQuant 在 8x64 和 16x64 也顯著贏過各規則在 1x16 的結果（1x16 需要新硬體），三個模型、兩個資料集都成立。
- 256x64 也成立，只有 Phi-4 的 C4 不顯著。
- 注意：FlipQuant 使用了校準資料（open-web-math 與 codeparrot，不含 WikiText 和 C4），而這些規則完全不需要資料。

### GEMM overhead 的歷次量測對照（相對 stock NVFP4）

| 來源 | GPU | 量測方式 | 16x64 | 8x64 |
|---|---|---|---|---|
| Kernel 報告開頭的「1.0–4.9%」 | RTX 5090 | 大方陣 TFLOP/s，舊設定 | 5090 上 16 列 × 64 K：+0.59% | — |

| Item #3 診斷 | RTX PRO 6000 | CUPTI 連續呼叫，全部 E2M1 | +2.8 到 +3.7% | +4.3 到 +11.6% |
| C2 | RTX PRO 6000 | CUPTI、輪替 3 輪、4096³ | +3.0%（全 E2M1）/ +3.7%（真實 map） | — |
| C1（目前版本） | RTX PRO 6000 | CUPTI 連續 20 次、輪替、最密集模組、整個 forward 加總 | T ≥ 2048：+3.6 到 +4.8% | +10.4 到 +12.9% |
| 端到端 prefill（CUDA graph） | RTX PRO 6000 | 整個模型（1×1024 以上，FourOverSix activation） | +1.4 到 +2.8%（Qwen +0.8 到 +1.2%） | +3.8 到 +7.6%（同 placement；Qwen +2.3 到 +3.0%） |

**差異的原因**
1. **GPU 不同。** Kernel 報告指出，同一個 kernel 在 PRO 6000 上的 overhead 比 5090 高（+8.6% 對 +0.59%）。它的推測是：PRO 6000 的 tensor 吞吐量高約 21%，但 shared memory 頻寬沒有等比例增加。這點沒有 profile 驗證。
2. **量測方式不同。** Item #3 的結論是，單獨呼叫最穩定，也和端到端最一致。CUPTI 連續呼叫會把呼叫之間的等待也算進去，而且更容易撞到 500 W 的功耗上限。
3. **C1 選的是最壞情況。** C1 用最密集的模組，這會比全部 E2M1 多 0.6–1.9 pp。
4. **Cache 狀態不同。** C1 用同一份權重連續跑 20 次，權重一直留在 L2。

**GEMM 和端到端大致一致。** GEMM 約占 prefill 的 25–38%（Llama、Mistral、Phi-4，T ≥ 2048；Qwen 為 16–20%）：
- 16x64：GEMM 約 +4.5%，對應端到端約 +1.2 到 +1.6%（實測 +1.4 到 +2.0%）。
- 8x64：GEMM 約 +11%，對應端到端約 +3.2 到 +4.3%（實測 +3.8 到 +5.7%）。

|---|---|---|---|
| **FlipQuant 16x64 對 FourOverSix** | −0.2 到 −0.6% | −0.1 到 −0.6% | −0.2 到 −0.4% |

- **16x64：** batch 1、4、16 時都和 FourOverSix 一樣用 16 寬的 tile，decode 幾乎不增加成本。
- **8x64：** 變慢主要來自權重放在 B（這種 kernel 只有 128 寬的版本，沒有窄 tile）。和同樣放 B 的 FourOverSix 相比，只差 0.6–3.1%。
- **FP4 相對 BF16 的加速：** batch 1 時最大；到 16×2048 時縮小，因為 KV cache 上的 attention 占了主要時間。
