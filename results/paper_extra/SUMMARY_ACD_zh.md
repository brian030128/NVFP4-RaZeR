### A-3. 機制

**Tile 內的偏好幾乎都是混合的。**
- 把 1x16 的選擇按 tile 分組，≥ 99.999% 的 tile 同時含有兩種格式。
- 少數格式在 tile 中的占比：IF4 和 Zou 是 36.5–38.1%，Zou + FourOverSix 是 42.1–46.4%。這接近各 block 獨立選擇時的預期值，表示偏好在 tile 尺度上並不聚集。

**加總誤差後，結果等於多數決。**
- IF4 和 Zou 有 62–63% 的 block 偏好均勻格式。粗化後，均勻格式的占比變成：8x64 為 91–94.5%，16x64 為 96–98.4%，256x64 為 99.1–99.7%。
- Zou + FourOverSix 在 1x16 是 53–54%。到 256x64 時，Llama 降到 41%，Mistral 降到 36%，Phi-4 反而升到 69%。
- IF4 + FourOverSix 和 Zou + FourOverSix 相同：
  - ≥ 99.999% 的 tile 是混合的，少數格式占 42.2–46.5%。
  - 均勻格式在 1x16 是 53–54%。到 256x64 時，Llama 為 41%，Mistral 為 36%，Phi-4 為 67%。
- FlipQuant 的 E0M3 占比：8x64 為 1.6–2.5%，16x64 為 2.2–3.3%，256x64 為 6.4–10.0%。

**權重誤差預測不了 loss。**
- Zou + FourOverSix 在 8x64 的權重平方誤差比 FourOverSix 少 3.7–4.4%，但 ΔNLL 落在 −0.0016 到 +0.0029：6 組中只有 1 組顯著較好，2 組顯著變差。
- IF4 + FourOverSix 在 8x64 的權重誤差也比 FourOverSix 少 3.7–4.4%，同樣沒有換來顯著的增益，只有 Phi-4 的 C4 是例外。
- FlipQuant 在 8x64 的權重誤差和 FourOverSix 幾乎一樣（−0.0% 到 +0.1%），卻全部顯著較好：
  - Llama：−0.0141 / −0.0141
  - Mistral：−0.0059 / −0.0058
  - Phi-4：−0.0077 / −0.0049

### A-4. 事後分析（未登錄）

- FlipQuant 在 8x64 和 16x64 也顯著贏過各規則在 1x16 的結果（1x16 需要新硬體），三個模型、兩個資料集都成立。
- 256x64 也成立，只有 Phi-4 的 C4 不顯著。
- 對 IF4 + FourOverSix 的 1x16：8x64 和 16x64 同樣全部顯著；256x64 在 Phi-4 的兩個資料集都不顯著。

### C1. 每次 forward 的 GEMM 時間（論文 §4.3）

**執行資訊**
- **主要數字來自 deviation 2**（`results/paper/PROTOCOL_GEMM_ISOLATED.md`）。
  - Commit：登錄 `c00b872`，方法修正 `46a35a1`；結果和本檔在同一個 commit。
  - 數字在 `results/paper/tables/main.md`。256x64、逐形狀細節、模組標籤與 GPU 遙測在 `appendix.md`。
- **量測方式：**
  - 每次呼叫單獨執行：GPU 閒置時才啟動，前後都同步，用 CUPTI 計 kernel 本身的時間。
  - 冷 L2：每次呼叫換用不同的權重副本（總量 ≥ 4 倍 L2），並在呼叫前讀取 512 MiB 的緩衝區，清空 L2。
  - 每次呼叫都重新產生 activation 並量化。和真實 forward 一樣，activation 在 L2，權重在 DRAM。
  - 輪替順序 3 輪，每輪 30 次，取中位數。
- **Map 的模組：**
  - 「典型」：每種投影中，E0M3 比例為中位數（取較小的中位數）的模組。
  - 「最壞」：最密集的模組。
- **冷 cache 驗證（登錄的第 1 步）：**
  - 第一版方法（只 flush、同一份權重）在 Llama q_proj、T = 2048 沒通過：輪替權重副本比 flush 慢 2.1–4.3%。
  - 診斷顯示，差異來自 flush 之後的時脈／功耗狀態，不是位址不同：輪替 + flush 和只 flush 的結果相同。
  - 依使用者的決定改用「輪替 + flush」，重跑後 8/8 通過。
- **檢查：** 1,890 組（投影、T、設定）的輸出都和 NativeLinear 逐位元相同；GPU 上沒有其他程式。
- **舊版保留為替代方法。** 舊版（deviation 1：CUPTI、連續 20 次呼叫、輪替 3 輪）標註為「CUPTI、連續呼叫、L2 warm、最密集模組」，放在附錄。更早的固定順序版本在 `results/paper/tables/gemm_superseded.md`。

  - 4×2048 時，16x64 和 256x64 兩者相差在 1 pp 以內（0.2–0.7 pp）；8x64 為 0.6–1.8 pp。
  - 1×128 時，GEMM 高估了 0.9–5.8 pp；1×256 時，介於高估 3.3 pp 與低估 1.8 pp 之間。

**差異的原因**
1. **GPU 不同。** Kernel 報告指出，同一個 kernel 在 PRO 6000 上的 overhead 比 5090 高（+8.6% 對 +0.59%）。它的推測是：PRO 6000 的 tensor 吞吐量高約 21%，但 shared memory 頻寬沒有等比例增加。這點沒有 profile 驗證。
2. **量測方式不同。**
   - Item #3 的結論是，單獨呼叫最穩定，也和端到端最一致。CUPTI 連續呼叫會把呼叫之間的等待也算進去，而且更容易撞到 500 W 的功耗上限。
   - C1 新版實測：改成單獨呼叫加冷 L2 後，T ≥ 2048 時 16x64 低 0.0–1.0 pp，8x64 低 1.2–2.9 pp；T = 128 時 16x64 從 +9.4 到 +11.4% 降到 +1.6 到 +4.5%。
   - Item #3 的事件計時（event pair）每次呼叫會多算 24–31 µs 的主機排程時間，在小 T 不適用，所以新版改用 CUPTI。
3. **C1 舊版選的是最壞情況。** 舊版用最密集的模組。新版的量測顯示，最密集模組比典型模組多 0.0–0.7 pp（16x64）、0.3–1.2 pp（8x64）。
4. **Cache 狀態不同。** 舊版用同一份權重連續跑 20 次，權重一直留在 L2。冷 cache 驗證顯示：權重不在 L2 時，gate_proj 在 T = 128 慢 42–44%，q_proj 在 T = 2048 慢 7–15%，gate_proj 在 T = 2048 則沒有差別。

**GEMM 和端到端：16x64 一致，8x64 有差距。** 以新版計算，GEMM 約占 prefill 的 27–41%（Llama、Mistral、Phi-4，T ≥ 2048；Qwen 為 17–22%）：
- 16x64：GEMM 約 +3.0 到 +4.4%，折合 prefill 的 +1.0 到 +1.8%；端到端實測 +1.4 到 +2.0%（Qwen：+0.6 到 +0.7% 對 +0.8 到 +1.1%）。
- 8x64：GEMM 約 +8.6 到 +10.7%，折合 prefill 的 +2.9 到 +4.2%；端到端實測 +3.8 到 +5.7%（Qwen：+1.6 到 +1.9% 對 +2.3 到 +3.0%）。端到端比單獨的 GEMM 多，原因尚未查明。
